# Software life-cycle record — IEC 62304

The IEC 62304 §5.1 development-plan record for `care-pathway-service`, and
the index of the evidence artefacts the standard's other clauses call for.
The regime detail is in
[`agents/share/compliance-for-healthcare.md`](../../../agents/share/compliance-for-healthcare.md)
§2.4; the repository-wide status is
[`spec/compliance` §8.4](../../../spec/compliance/index.md).

> **This is preparation, not conformity assessment.** Declaring a safety
> classification and maintaining the artefacts below does not make this
> software a registered medical device, and nothing here should be read as
> claiming it is. See §5.

## 1. Safety classification

**Declared: Class A** by default, configurable per deployment with
`CARE_PATHWAY_SAFETY_CLASS`. The running value and its rationale are
reported at `GET /api/compliance`.

| Class | When it applies to this service |
|---|---|
| **A** — no injury possible | The **template registry alone**: pathway definitions are reference data. No individual patient is tracked, and no output drives an individual's treatment, so a software failure cannot injure anyone. |
| **B** — non-serious injury possible | The **instance layer** is in use (`pathway_instances`, `instance_steps`): an individual patient's progress through a pathway is tracked, so a failure could contribute to a missed or mistimed step. |
| **C** — death or serious injury possible | A deployment relies on pathway output in a context where failure could contribute to death or serious injury. Requires the full Class C process and an ISO 14971 risk file, neither of which this repository provides. |

**The line that matters.** A registry of templates is generally not a
medical device. It becomes one when a deployment surfaces pathway steps as
**clinical decision support**, or tracks an individual patient through a
pathway. EU MDR **Rule 11** then puts it in Class IIa or above (see MDCG
2019-11 for qualification); the UK route is UKCA / MHRA plus NHS DTAC; the
US route is the FDA's SaMD and Clinical Decision Support framing.

A deployment that enables the instance layer **must** re-classify. The
default is deliberately the conservative-for-us reading (Class A for the
template registry) rather than an optimistic one, and the classification is
surfaced at runtime precisely so nobody has to guess which reading a given
deployment adopted.

## 3. Supply chain

- **SBOM** — CycloneDX 1.5, generated by `scripts/sbom.sh` and served at
  `GET /api/compliance/sbom`. Derived at compile time from this crate's own
  `Cargo.lock`, so it **cannot drift** from the binary that reports it.
- **SOUP annotations** — `compliance/soup.tsv` records the §8.1.2 purpose
  and safety-relevance note for every **direct** dependency. Adding a
  dependency without annotating it fails
  `soup::tests::every_direct_dependency_is_annotated`; removing one without
  cleaning the register fails `register_has_no_stale_entries`.
- **Boundary, stated plainly.** Transitive dependencies appear in the SBOM
  but are **not** individually assessed. Claiming to have reviewed several
  hundred crates would be false.
- **Gating** — `deny.toml` (`cargo-deny`) checks advisories and licences;
  every crate root carries `#![forbid(unsafe_code)]`.

## 4. Reproducible and signed builds

`scripts/build-reproducible.sh` pins the toolchain (`rust-toolchain.toml`),
derives `SOURCE_DATE_EPOCH` from the commit rather than wall-clock time,
records `BUILD_SHA`, and remaps absolute build paths out of the binary.
`--verify` builds twice and compares hashes.

The artefact reports `reproducible_release: true` at `GET /api/compliance`
only when it carries a known commit, a pinned `SOURCE_DATE_EPOCH`, and a
non-debug profile — so the claim is evidence, not assertion.

**Signing is out of scope for this repository.** Signing keys are a
deployment secret and must not be handled by a repository script
([`agents/share/security.md`](../../../agents/share/security.md) §5). Sign
in the release pipeline and publish the signature alongside the SBOM.

## 5. What is not here

- **No ISO 14971 risk file, hazard analysis, or risk-control trace.** The
  hazards this service could contribute to (a false pathway match, a
  missed instance step, an unauthorised disclosure) are real, and the
  controls exist in code — but relating them to clinical harm is a
  clinical judgement the operating organisation makes, not one a
  repository can assert.
- **No §9 problem-resolution process records.** Defect intake, analysis,
  and verification live in the operating organisation's quality system.
- **No conformity assessment, notified-body involvement, or technical
  documentation file.**
- **No usability engineering file** (IEC 62366-1).

These are the artefacts a qualification would otherwise have to
reconstruct after the fact. Building the machine-checkable half now —
SOUP, SBOM, traceability, reproducible builds — is what makes that
reconstruction feasible instead of archaeological.
