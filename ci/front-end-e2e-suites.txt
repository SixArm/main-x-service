# case-folder/case-folder-front-end-with-svelte — its playwright.config.ts
# assumes a live Loco JSON API on http://localhost:5150 with the seed
# task already run (`global-setup.ts` pings /healthz and verifies seed
# state before any test runs, so a misconfigured environment fails fast
# rather than producing a wall of stale assertions). This stage has no
# backend to offer it. Enrol once a dedicated job stands up
# case-folder-service-with-rust + Postgres + seed data alongside it —
# out of scope for this stage's install/check/vitest/build/lint/e2e
# shape, which assumes a front-end can be fully verified standalone.
#
# A note on how these fifteen were actually verified, for whoever adds
# the sixteenth: running every front-end's e2e suite back-to-back on one
# machine surfaced two false negatives that were not real defects —
# (1) Playwright's `reuseExistingServer` (true off CI) silently reusing
# a *different* project's still-running preview server left over from an
# earlier, unrelated run, so a later suite exercised the wrong app
# entirely; fixed by setting `CI=1` (which forces a fresh server and
# fails loudly on a port collision instead of reusing one) and killing
# any stray preview server between runs. (2) different front-ends pin
# different `@playwright/test` versions, and installing one project's
# dependencies can prune a Chromium revision another project's suite
# still needs from the shared `~/Library/Caches/ms-playwright` cache;
# fixed by running `pnpm exec playwright install chromium` immediately
# before each project's own suite, exactly as the CI steps in
# `.github/workflows/ci.yml` / `.woodpecker.yml` already do per job
# (each CI job gets its own fresh container, so this is a purely local,
# shared-cache artefact — it would not reproduce there).
